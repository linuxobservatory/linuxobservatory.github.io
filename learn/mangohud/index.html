How to read a MangoHud overlay

Understand FPS, frame time, GPU load and VRAM in a Linux gameplay recording—and what those numbers cannot tell you.

LINUX OBSERVATORY · EXPLANATORY GUIDE · UPDATED NOVEMBER 2026 · NO BENCHMARK DATA USED

A game fills the screen. Small numbers sit in a corner: FPS, GPU, CPU, VRAM, milliseconds. That is not decoration. It is a quick view into what the computer is doing.

What is MangoHud?

MangoHud is an open-source overlay for supported Vulkan and OpenGL programs. It can display information such as frame rate, frame timing, resource use and temperatures. It can also log measurements depending on how it is configured. The available sensors and accuracy vary with hardware, driver, game API and system configuration.

In Linux Observatory recordings, an overlay lets the viewer compare the visible game with measured state. When the game appears to hitch, the viewer can check whether a timing readout changes. When a resolution increases, they can watch how resource demand responds.

Read the overlay in this order.

  1. FPS: how quickly frames are being produced over an interval. A useful headline, never a full explanation of smoothness.
  2. Frame time: timing information associated with frames. A spike may help locate an unusual delay.
  3. GPU use: an estimate of graphics engine activity. High utilization does not tell you which operation is consuming the time.
  4. VRAM: GPU memory accounting. Be careful: allocation, reservation and actual use may not be the same quantity.
  5. CPU and RAM: system state that can matter when the bottleneck is not solely the graphics hardware.

What the readings do not prove

A GPU at 99% might suggest the graphics hardware is busy, but it does not prove that every slowdown is GPU-bound. A frame-time spike may appear when shaders compile, when the program waits for data, or because of many other factors. Likewise, a large VRAM number is not automatic evidence that physical memory has been exhausted.

Sensor polling cadence is another complication. An occasional CPU or GPU utilization sample is not equivalent to per-frame timing. On-screen metrics may be smoothed or refreshed at different intervals. Treat them as different kinds of observations rather than interchangeable measurements.

A useful way to inspect a recording

Start watching normally, without trying to read every number. Choose one specific event: a camera turn, loading transition or burst of effects. Replay that moment. Did the game visibly hitch? What did the frame-time graph do? Were settings or resolution identified? Does the symptom recur?

If the answer is “I saw a hitch, but I cannot tell why,” that is a responsible conclusion. It makes the next test more focused.

MangoHud versus other measurement tools

Linux Observatory has also used Gallium_HUD where applicable. Tools differ in API support, exposed counters, sampling and overhead. You should not assume the values from two overlays are directly interchangeable without checking their definitions and collection methods.

Read the MangoHud project documentation for configuration, supported metrics, frame-time logging and platform-specific limitations. The project’s own readouts, not a generic diagram, are the source for any claimed measurement in a Linux Observatory recording.

Takeaway

The overlay provides clues in context. The game footage provides the scene. Together they are more informative than an isolated FPS screenshot.

What is RADV in Linux gaming?

A plain-language explanation of Mesa RADV, Vulkan, Proton and the AMD graphics driver stack.

LINUX OBSERVATORY · EXPLANATORY GUIDE · UPDATED NOVEMBER 2026 · NO BENCHMARK DATA USED

If you have ever watched a Linux gaming video and seen “Mesa,” “RADV,” “Vulkan” or “Proton” in the description, you may have wondered whether they all do the same job. They don't.

RADV is a graphics driver.

RADV is a userspace Vulkan driver for many AMD graphics cards. It belongs to the open-source Mesa graphics project. Its job includes helping turn a game's Vulkan requests into commands that supported AMD graphics hardware can execute.

To use an analogy, a game is a person describing a picture; Vulkan is a shared technical language; RADV is an implementation that understands this language and knows how to instruct the particular GPU. This is an analogy, not an exact description of the API boundary.

Then what is Mesa?

Mesa is not a single driver. It is a collection of graphics implementations and related components used across Linux systems. RADV is one of them. The Linux kernel also has an amdgpu driver, but that is a different piece: kernel-mode and userspace drivers divide responsibilities.

Mesa's RADV documentation describes the division. The userspace driver handles hardware-specific graphics work such as shaders and command recording, while the kernel driver manages lower-level interactions and resources.

How can a Windows game use RADV?

Many Windows PC games use Direct3D, a graphics API associated with Windows. Under Steam's Proton compatibility environment, graphics translation components can convert those requests into Vulkan calls. DXVK covers Direct3D 9, 10 and 11; VKD3D-Proton is used for Direct3D 12. RADV can then implement the Vulkan requests for an AMD card.

The route is roughly:

Windows game → Proton / Wine
             → DXVK or VKD3D-Proton (if applicable)
             → Vulkan
             → Mesa RADV
             → amdgpu / AMD GPU

Not every game follows that exact path. Native Vulkan games may bypass those Direct3D translation components. Native OpenGL games use an OpenGL driver instead. External compositors and the display protocol introduce additional layers that this simple map leaves out.

Why does the Mesa version matter?

Graphics-driver updates can include bug fixes, performance changes, support for new hardware and application workarounds. A game that misbehaves with one Mesa build may behave differently with another. But seeing a difference between two videos does not prove that Mesa alone caused it unless the workload and other conditions were controlled.

That is why Linux Observatory pays attention to software versions. Game patches, kernel updates, Proton variants, settings and driver changes may all affect the outcome. A clear recording description makes observations easier to compare without pretending they are controlled when they are not.

What can you actually observe?

A recording can show a game launching, rendering frames, stuttering or failing under a documented environment. It can show an overlay's displayed utilization or timing readings. It cannot reveal every internal driver decision from the outside. Driver-level causation often needs logs, profiling, controlled reproduction and maintainer analysis.

Reliable places to learn more

  • Mesa RADV official documentation
  • Valve Proton repository
  • DXVK repository
  • VKD3D-Proton repository
Takeaway

Proton helps run many Windows games. DXVK or VKD3D-Proton can translate Direct3D into Vulkan. RADV implements Vulkan for supported AMD GPUs. Different layers, different jobs.
